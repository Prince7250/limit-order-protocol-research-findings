## Findings

### LOP-01 — zkSync witness proxy selects a different Permit2 domain from the supported SDK address

| Field | Assessment |
|---|---|
| Status | **Confirmed address-selection discrepancy; not a confirmed exploitable vulnerability** |
| Severity | Low / operational interoperability, conditional on deploying and using the witness helper on zkSync |
| Affected code | `contracts/extensions/Permit2WitnessProxy.sol:22`; `deploy/deploy-Permit2WitnessProxy.js:22-32` |
| Preconditions | A witness proxy is deployed on chain ID 324 while a user or integration follows the normal SDK/Uniswap zkSync address when approving and signing Permit2 data. No checked-in zkSync witness-proxy artifact was found. |

#### Address resolution verified

Uniswap's [Permit2 deployment reference](https://developers.uniswap.org/docs/protocols/permit2/overview) states that its supported chains use `0x000000000022D473030F116dDEE9F6B43aC78BA3`, except zkSync, which uses `0x0000000000225e31D15943971F47aD3022F714Fa`. This exactly matches the code in the published `@uniswap/permit2-sdk@1.3.0` artifact pinned by this repository: `permit2Address(324)` returns the latter and all other IDs return the former.

For every LOP chain ID configured in `config/constants.json`, the resolved address is:

| Configured chain IDs | `permit2Address(chainId)` in the pinned SDK |
|---|---|
| `1`, `10`, `56`, `100`, `130`, `137`, `146`, `250`, `8217`, `8453`, `31337`, `42161`, `43114`, `59144`, `1313161554` | `0x000000000022D473030F116dDEE9F6B43aC78BA3` |
| `324` (zkSync Era) | `0x0000000000225e31D15943971F47aD3022F714Fa` |

`31337` is the local Hardhat configuration, not a claim that Uniswap publicly supports that chain. The table is the exact behavior of the repository's pinned SDK switch for the chain IDs the deployment configuration contains.

`Permit2Proxy` receives this SDK-selected address in `deploy/deploy-Permit2Proxy.js:23,29,43`. `Permit2WitnessProxy` instead has a constant canonical address, and its constructor accepts only `IMMUTABLE_OWNER`; its zkSync branch at `deploy/deploy-Permit2WitnessProxy.js:22-32` cannot override that address. The executed reproducer confirms this literal mismatch against the pinned SDK behavior.

#### Constructor and runtime trace

The witness proxy constructor stores the LOP router as `IMMUTABLE_OWNER` and verifies that the deliberately obfuscated helper selector equals `IERC20.transferFrom` (`0x23b872dd`). At runtime, only that immutable router may call `func_801zDya`. The function forwards the maker (`from`), settlement recipient (`to`), requested amount, Permit2 permit, witness hash, fixed witness-type string, and signature to `_PERMIT2.permitWitnessTransferFrom`. The permit's spender must be the proxy, and the Permit2 signature must be produced for the exact Permit2 contract selected by `_PERMIT2`; the SDK's typed-data domain includes `verifyingContract`.

`test/WitnessProxyExample.js` deploys the helper locally and signs with the SDK's deprecated `PERMIT2_ADDRESS` constant (the canonical address). It neither exercises the zkSync deployment branch nor proves interoperability with `permit2Address(324)`.

#### zkSync result and impact

The initial concern that the canonical address might have no code on zkSync is **refuted**. Read-only zkSync mainnet queries on 2026-10-25 found code at both addresses. The explorer's verified metadata identified each as `src/Permit2.sol:Permit2` and exposed both `permitWitnessTransferFrom` overloads. `DOMAIN_SEPARATOR()` succeeded at both addresses but returned different values: `0xadbe17760d87cd246046b5e2cec81951fac0588a9abe91e30ec1c5bd71aaa14c` for the canonical address and `0xef23dd8266066484b254d36dce205d0f590263edb312139dbe5b1479a491928b` for the zkSync-specific address.

The witness proxy is therefore not inherently unable to make an external call, and this review has no evidence that it targets an arbitrary or malicious contract. It is nevertheless incompatible with the standard zkSync SDK path: a maker who approves the official zkSync Permit2 and signs typed data with `permit2Address(324)` has authorized the alternate address, whereas this helper calls the canonical one. The canonical contract has separate allowance and nonce state, and the signature domain differs. Such a fill should fail unless the maker instead separately approves and signs for the canonical Permit2 instance.

This is a conditional availability/integration defect, not a demonstrated funds-loss path. It requires a zkSync witness-proxy deployment plus an integration that follows the documented SDK address. A signature deliberately made for the canonical contract still binds its spender, token, amount, nonce, deadline, and witness; no bypass of Permit2 authorization was established. The absence of a checked-in zkSync witness-proxy deployment also prevents a claim about deployed user funds.

**Remediation:** make the Permit2 address an immutable constructor parameter, pass `permit2Address(Number(chainId))` from the deployment script, and add a zkSync integration test that approves, signs, and fills through the same address. Existing proxy instances are immutable, so correcting an already deployed helper requires a new deployment and an off-chain address/signing update. If retaining the canonical zkSync instance is intentional, document it explicitly, make the signing client select it deliberately, and verify its bytecode/provenance as part of the deployment release.

### LOP-02 — Permit2 proxy deployment script's chain-ID guard is ineffective

| Field | Assessment |
|---|---|
| Status | **Confirmed** source defect |
| Severity | Low / operational security |
| Affected code | `deploy/deploy-Permit2Proxy.js:14-21` |
| Attacker capability | None required; an operator can accidentally deploy using mismatched RPC/network settings. |

The exact expression in `deploy/deploy-Permit2Proxy.js:15-16` is:

```js
networkName in hre.config.networks[networkName] &&
    chainId !== hre.config.networks[networkName].chainId.toString()
```

JavaScript's `in` tests whether its left operand is a property name on the object at its right operand (including the prototype chain); it does not test whether the per-network object exists in its parent. With a normal configuration such as `{ mainnet: { chainId: 1, url: ... } }`, the expression asks whether property `mainnet` exists inside `{ chainId, url }`, returns `false`, and short-circuits before comparing chain IDs. `deploy.js`, `deploy-helpers.js`, `deploy-fee-taker.js`, and `deploy-native-order-factory.js` use the intended parent-object check:

```js
networkName in hre.config.networks &&
    chainId !== hre.config.networks[networkName].chainId?.toString()
```

The dependency-free mocked-Hardhat regression test was executed with `networkName = 'mainnet'`, configuration `mainnet.chainId = 1`, and an RPC result of `31337`. Its actual result was `current guard=false, corrected guard=true`. It also demonstrates that the flawed condition happens to be true only if the individual network configuration contains a property named `mainnet`; that is accidental object shape, not reliable protection.

This is not an externally exploitable bypass: a remote actor does not control the deployer's Hardhat configuration or RPC endpoint through the contract. It simply fails open for ordinary operator misconfiguration. It also does not automatically bind Permit2 to the configured-but-wrong chain: after the guard, the script uses the RPC-returned `chainId` for both `permit2Address(Number(chainId))` and `ROUTER_V6[chainId]`. On a different supported chain, the transaction can therefore deploy a coherent proxy on an unintended network while the deployment name, artifacts, verification context, and operator intent correspond to another network. On an unsupported chain, missing constants are likely to make the script fail later rather than safely skip before deployment.

**Remediation:** replace the condition with the peer-script form above, retain optional chaining for defensive handling, and keep the executed mocked-HRE regression test (or migrate its cases into the normal test framework when dependencies are available). Treat an RPC/name mismatch as a hard failure before any deployment helper, artifact write, or verification action.

### LOP-03 — Native-order documentation is stale relative to code

| Field | Assessment |
|---|---|
| Status | **Informational** |
| Severity | Informational |
| Affected material | `native-swap.md`; `NativeOrderImpl.sol:36`, `122-153`; `NativeOrderFactory.sol:69-76` |

The markdown says resolver compensation is capped at `basefee * 30,000 * 1.1`, but source uses `_CANCEL_GAS_LOWER_BOUND = 70_000`. It also describes a clone `rescueFunds` function and resolver-restricted recovery that do not exist in the present implementation; `rescueFunds` is instead factory-owner-only and applies to factory-held balances. The documentation must not be used as behavioral authority.

**Mitigation:** regenerate/rewrite the native-order guide from tests and source, including the exact reward formula, caller roles, and factory-vs-clone fund boundaries.

## Important reviewed controls (not findings)

- **Domain separation:** standard orders include chain ID and LOP address, preventing ordinary cross-chain/contract replay.
- **Extension integrity:** extension bytes are bound by a 160-bit truncated Keccak commitment plus the `HAS_EXTENSION` flag. A substitution requires a targeted 160-bit collision under normal assumptions.
- **State before interactions:** invalidators are written before callbacks and transfers, preventing a successful reentrant double fill in normal/remaining paths.
- **First-fill permit special case:** remaining orders check that maker permit execution did not create a fill before proceeding; an enclosing bit-order transaction rolls back if an inner fill consumes its bit.
- **Atomicity:** all transfers/callbacks execute in one transaction; any failure rolls back the invalidator update and asset movements.
- **Callback capability is deliberate:** targets, predicates, getters, and proxy suffixes are maker-committed extension data, so their arbitrary external calls are an explicit maker policy rather than a generic untrusted-input bug.

## Hypotheses and design risks

| ID | Status | Assessment and Verified Behavior |
|---|---|---|
| H-01 | **Excluded Scope** | Fee-on-transfer, rebasing, or dishonest ERC-20s can cause received balances to diverge from nominal transfer amounts. LOP does not measure pre/post balances. Immunefi's official bug bounty rules explicitly list "Lack of support for Fee-on-Transfer (FoT) tokens" as an **out-of-scope impact**. |
| H-02 | **Refuted as Vulnerability (Informational Code Quality)** | `OffsetsLib.get` lacks a `begin <= end` monotonicity check: if $begin > end$, `sub(end, begin)` underflows in EVM assembly to $2^{256} - (begin - end)$. However, rigorous analysis and executable boundary tests (`analysis/tests/extension-parser-boundaries.test.js`) prove that all downstream consumers (`makerAssetSuffix`, `takerAssetSuffix`, `makingAmountData`, `takingAmountData`, `predicate`, `makerPermit`, `preInteractionTargetAndData`, `postInteractionTargetAndData`, `customData`) either invoke `calldatacopy` or perform ABI-encoding to memory. Any allocation of $2^{256}$ words in EVM immediately triggers an Out-Of-Gas revert during memory expansion. No out-of-bounds memory can be read, no state corruption occurs, and no funds are drained. **Remediation:** Add `if gt(begin, end) { mstore(0, exception) revert(0, 4) }` in `OffsetsLib.sol` for clean, explicit error reporting. |
| H-03 | **Closed / Verified Invariants with Documented Operational Edge Cases (Informational / Low)** | Comprehensive mathematical tracing and automated boundary/fuzz test suites (`analysis/tests/pricing-and-calculators.test.js`, 21 passing checks) prove the security invariants across dynamic price calculators and arithmetic libraries:<br>1. **AmountCalculatorLib Partial-Fill Invariant:** Fuzz testing confirms that linear taking amount calculations (`(swapMakerAmount * orderTakerAmount + orderMakerAmount - 1) / orderMakerAmount`) strictly round UP (ceil division), guaranteeing $\sum \text{takingAmount}_i \ge \text{orderTakerAmount}$ (maker receives at least the full expected order amount; taker pays up to $N-1$ wei extra). Making amounts floor round, ensuring takers never receive more than the exact fraction.<br>2. **RangeAmountCalculator Arithmetic Underflow:** In `getRangeMakerAmount`, the closed-form quadratic solution `Math.sqrt(...) - bDivK - alreadyFilledMakingAmount` suffers from integer division truncation across its five intermediate steps. When taking amounts are dust (evaluating to $< 1$ maker unit), `Math.sqrt(...)` evaluates to 1 unit less than `bDivK + alreadyFilledMakingAmount`, causing an unsigned integer underflow outside unchecked blocks and reverting with `Panic(0x11)`. In normal settlement, returning 0 would have triggered `SwapWithZeroAmount()` in `OrderMixin` anyway; the revert is fail-safe and prevents unauthorized transfers.<br>3. **RangeAmountCalculator Decimal Scaling Assumption:** The contract divides by `2e18` and scales by `1e18`, implicitly assuming that the maker token has 18 decimals or that the maker has pre-scaled $P_{start}, P_{end}$ by $10^{18 + (18 - \text{makerDecimals})}$. For non-18 decimal maker tokens without pre-scaling, calculated taking amounts will be small. This is an optional helper calculator and parameter configuration caveat (out-of-scope bounty exclusion).<br>4. **ChainlinkCalculator:** Enforces a strict 4-hour staleness threshold (`_ORACLE_TTL = 4 hours`, reverting with `StaleOraclePrice`). Negative prices revert via OpenZeppelin `SafeCast.toUint256()`. Decimals mismatches in double-price feeds revert via `DifferentOracleDecimals`.<br>5. **DutchAuctionCalculator:** Implements linear decay bounded to `[startTime, endTime]`. Time clamping prevents out-of-bounds evaluations. Rounding directions strictly favor the maker (floor for making amount, ceil for taking amount). Checked arithmetic prevents overflow.<br>6. **AmountGetterWithFee & FeeTaker:** Fee percentages are uint16 ($\le 65,535$), preventing denominator overflow. Calldata out-of-bounds slicing reverts safely. WETH unwrapping and ETH fee transfers in `FeeTaker` are atomic, rolling back on failure via `EthTransferFailed`. |
| H-04 | **Confirmed Informational / Low (Griefing Edge Case)** | When an expired native order is cancelled via `NativeOrderImpl.cancelExpiredOrderByResolver`, remaining funds are unwrapped from WETH and transferred via raw `call{value: balance}("")` to the maker address `makerOrder.maker.get()`. If the maker is a contract that rejects ETH (no payable receive/fallback or explicit revert) or consumes excessive gas, `(bool success, ) = maker.call{value: balance}("")` returns `false`, causing the transaction to revert with `Errors.ETHTransferFailed()`. Automated regression tests in `analysis/tests/native-order-cancellation.test.js` prove:<br>1. **Impact Scope:** Affected scope is strictly limited to the individual minimal proxy clone. No shared balances or other orders can be blocked (verified in Scenario F).<br>2. **Reentrancy Immunity:** Reentrant calls during the ETH transfer to `cancelOrder` or `cancelExpiredOrderByResolver` safely revert with `CanNotCancelForZeroBalance()` because WETH balance is unwrapped and zeroed before the external call (verified in Scenario E).<br>3. **Fund Safety:** Maker funds are not permanently locked because the maker contract can still retrieve WETH via `NativeOrderImpl.withdraw()` (verified in Scenario C).<br>4. **Bounty Eligibility:** Resolvers who simulate transactions before broadcasting will detect the revert and skip the call without incurring gas. This is not a Critical/High impact (no theft of funds, no protocol insolvency, no permanent fund locking). **Remediation:** In `_cancelOrder`, consider wrapping the maker ETH transfer in a try/safe transfer or leaving unwithdrawn balances claimable via pull-payment pattern. |
| H-05 | **Closed / Verified Non-Vulnerability (Defensive Protocol Design)** | Pausing (`whenNotPaused()`) is applied strictly to `_fill` entry points in `OrderMixin.sol`. It prevents new order executions during emergency conditions. Crucially, order cancellation functions (`cancelOrder`, `cancelOrders`, `bitsInvalidateForOrder`, and `epochManager`) do NOT have the `whenNotPaused` modifier and remain 100% operational while trading is paused (reproduced in automated test `Pausing vs Cancellation Protocol Sovereignty Invariant`). The contract holds no custody of user maker assets (funds remain in maker wallets until settlement). The protocol owner has no privileged access to withdraw or redirect user assets. |
| H-06 | **Closed / Verified Cross-Component Invariants (Safe Defensive Architecture)** | Investigated multi-step interactions across order authorization, dynamic extension parsing, partial fills, callbacks, and token transfers (`analysis/tests/cross-component-invariants.test.js`, 6 passing tests):<br>1. **Flash-Swap Reentrancy Capping:** Checks-Effects-Interactions strictly enforced (`OrderMixin.sol:338-342`). Order invalidator state (`_bitInvalidator` or `_remainingInvalidator`) is updated at Step 5 before pre-interactions, token transfers, or `takerInteraction` callbacks. Reentrant fills attempted inside `takerInteraction` are strictly bounded to the unconsumed remaining making amount ($\sum \text{fills} = \text{order.makingAmount}$). Reentrancy against single-fill orders immediately reverts with `BitInvalidatedOrder()`.<br>2. **Settlement Atomicity & Default Rollback:** In flash swaps, maker tokens are delivered to the taker in Step 7 before taking tokens are pulled in Step 9. If the taker callback or payment defaults, the transaction reverts with `TransferFromTakerToMakerFailed()`, completely rolling back prior token transfers and invalidator updates.<br>3. **Extension Immutability Across Partial Fills:** Even though ECDSA signature recovery is skipped on subsequent partial fills (`remainingMakingAmount < order.makingAmount`) for gas efficiency, `order.isValidExtension(extension)` (`OrderMixin.sol:275`) is enforced unconditionally on every fill. Modifying extension bytes across fills fails with `InvalidExtensionHash()`.<br>4. **EIP-1271 Signature Lifecycle vs Cancellation Sovereignty:** For smart contract wallets (`_fillContractOrder`), EIP-1271 signatures are verified on the first fill. Contract wallets revoking approval must call `swap.cancelOrder()` (which sets `_remainingInvalidator` to `type(uint256).max`), permanently stopping fills with `InvalidatedOrder()`.<br>5. **Caller Authentication on Invalidation:** Order cancellation (`cancelOrder`) is authenticated strictly against `msg.sender`. External contracts invoked during pre/post-interactions cannot cancel or manipulate orders on behalf of the maker. |
| H-07 | **Closed / Verified Invariants & Confirmed Known Design Constraints (Informational / Operational)** | Comprehensive audit and automated regression testing of Permit2 and Permit2WitnessProxy integration (`analysis/tests/permit2-signature-and-nonce.test.js`, 15 passing tests):<br>1. **End-to-End Signature Lifecycle & Witness Binding:** Traced SDK permit generation through `Permit2Proxy` and `Permit2WitnessProxy`. In `Permit2WitnessProxy`, `_WITNESS_TYPE_STRING` binds `Witness(bytes32 salt)` into Permit2's EIP-712 struct hash. Modifying the witness salt in calldata breaks signature recovery, reverting in Permit2 with `InvalidSigner()` and in LOP with `TransferFromMakerToTakerFailed()`.<br>2. **Cryptographic Domain Separation & Parameter Binding:** EIP-712 domain separation enforces `block.chainid` and `verifyingContract`. Cross-chain replay (e.g. signing with `chainId = 1` against local `31337`) is rejected. Permit2 derives `spender` directly from `msg.sender`; signing for any spender other than the deployed proxy reverts with `InvalidSigner()`. Expired deadlines (`deadline < block.timestamp`) revert with `SignatureExpired()`.<br>3. **Replay Protection & Cross-Order Permit Isolation:** Once an order fills, Permit2 burns the single-use nonce in `nonceBitmap[maker][wordPos]`. Replay of the order reverts in LOP (`BitInvalidatedOrder()`) and in Permit2 (`InvalidNonce()`). Reusing a victim's Permit2 signature in an unauthorized order fails because the attacker cannot forge the maker's signature on the enclosing limit order (`BadSignature()`).<br>4. **Multi-Transaction Partial Fill Incompatibility (OpenZeppelin L-02 Validation):** Demonstrated that an order configured with `allowPartialFills: true` can fill partially on the first transaction, but subsequent fills in separate transactions revert because the single-use Permit2 nonce is already consumed in Permit2 storage (`InvalidNonce()`). | H-08 | **Closed / Verified Authorization vs Settlement Invariants (Safe Defensive Architecture)** | Comprehensive review of signed order authorization versus actual on-chain settlement across 16 automated tests (`analysis/tests/order-authorization-and-settlement.test.js`):<br>1. **Access Control & Authorization:** Low-80-bit packing in `MakerTraits` strictly confines private orders to `allowedSender`; unauthorized callers revert with `PrivateOrder()`.
